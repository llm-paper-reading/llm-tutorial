# 前沿调研方法：信源、核查与报告写作

「前沿追踪」是这个站的第三个内容板块：[教程](/tutorials/gradient-descent)建立知识框架，[论文精读](/papers)纵向深挖一篇经典，前沿追踪则横向看一片——新模型发布、新论文趋势、榜单变化，先把线索攒起来，再核对一手来源，最后沉淀成一篇带引用的调研报告。<Cite n={1} />本篇说明这个板块怎么用：信源怎么分层、追踪保持什么节奏、数字怎么核查，以及一篇报告长什么样。

## 一、信源分层：一手优先，二手只做线索

大模型领域每天产出的「新闻」远多于「事实」。调研的第一条纪律是把信源分成两层：

| 层级 | 信源 | 用途 |
|---|---|---|
| 一手来源 | 论文原文、官方技术报告、官方博客、模型卡、项目 README | 数字与结论的**最终依据** |
| 二手来源 | 趋势榜单、每日情报、解读博客、社群讨论 | **发现线索**，不作为事实依据 |

一手来源里，arXiv 与官方技术报告给出模型结构、训练配方和 benchmark 的原始口径；模型卡与 README 补充部署细节。<Cite n={2} />二手来源的价值是覆盖面：Hugging Face Papers 的每日热门榜反映社区注意力，AI News 这类每日摘要帮你用最少时间不漏大事件。<Cite n={1,3} />原则只有一条：**二手来源里看到的任何数字，写进报告前必须回到一手来源核对**；核对不到就明确写「未见官方披露」。

## 二、追踪节奏：每日扫、每周筛、事件驱动深挖

前沿追踪不必全天候刷信息流，按三个粒度组织就够：

1. **每日扫（10 分钟）**：过一遍趋势榜与每日摘要，只做标记不做深读——判断「这条值不值得进调研池」。
2. **每周筛（1 小时）**：把调研池里的线索按主题归并（如同一系列模型发布、同一条技术路线），挑出值得展开的一两个主题。
3. **事件驱动深挖**：重大发布或争议出现时，围绕它拉起一篇调研报告——读原文、抄数字、做横向对比，几天内完成，趁上下文还热。

归并的标准不是「哪个最热」，而是「哪些线索指向同一个问题」。一篇报告只回答一个问题（例如「稀疏注意力这条路线现在走到哪了」），比罗列十条新闻有用得多。

## 三、核查原则：数字可溯源，口径不横比

写报告时的几条硬规矩，与全站的知识溯源规范一致：

- **数字必须可追溯**：参数量、训练 token 数、GPU hours、benchmark 分数、上下文长度、吞吐提升，都要能指到明确来源；追不到就删掉或改用「报告称」「论文给出」等限定表达。
- **不补造未公开细节**：loss 曲线、数据配比、teacher routing、系统架构——原文没说就是不写，猜测留给读者自己。
- **不同口径不直接横比**：不同 harness、token budget、工具条件或评测口径下的结果，不放进同一张排名表；要对比就先说明口径差异。
- **引用一手优先**：第三方博客只能作为补充或线索，核心论断的角标指向论文与官方资料。

## 四、调研报告的标准结构

一篇报告按下面的骨架写，读者可以在五分钟内判断「这篇解决什么问题、证据是什么」：

1. **背景与问题**：这个主题为什么现在值得看？前一个阶段的格局是什么？
2. **主线梳理**：按时间或技术路线组织关键事件 / 论文 / 发布，每个论断带引用角标。
3. **横向对比**：能放表格就放表格（模型、方法、指标），口径差异写进表注。
4. **结论与影响**：回答开篇的问题；不确定的部分明确列出待验证项。
5. **参考资料**：用 `<References>` 统一列出，并说明每个来源支撑的内容——与论文精读的格式完全一致。

图片和图表的规范也沿用全站约定：优先从原始论文抽取矢量图，图注先说内容再标来源。

## 五、如何新增一篇报告

两步，与新增一篇论文精读同构：

1. 在 `src/lib/frontier.ts` 的 `reports` 数组顶部插入新条目（`slug`、标题、描述、关键词、图标、日期），顺序即展示顺序，新报告放最上面；
2. 新建 `src/app/frontier/<slug>/page.mdx`，开头 `export const metadata = frontierMetadata("<slug>")`，正文按第四节的骨架写。

侧边栏、导航、上一篇 / 下一篇、sitemap 都由注册表自动生成，无需改其他文件。
