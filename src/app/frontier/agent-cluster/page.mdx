# 大规模 Agent 集群控制技术调研报告

> 📡 **调研信息**（2026-09-15，同日增补第六～八节，09-16 增补第九节）：browser-skill（真实 Chromium）逐项目直查 25+ 主流框架与协议项目的 GitHub 一手页面——README 全文、release/tag 版本、star/fork 数均为当日实时数据；增补部分另查 Anthropic / OpenAI 官方产品页与客户案例库、Claude Code / Codex 官方文档、openai/codex 源码常量。

> 📌 **前置与读法**：本报告是《[大模型推理与任务规划能力提升调研报告](/frontier/model-reasoning-planning)》的姊妹篇——那篇回答「模型如何获得多轮推理与规划能力」，本篇回答「多个 agent 如何组织成可控的集群」。多智能体的基础概念可先读站内[多智能体强化学习](/tutorials/multi-agent-rl)教程。只想做选型的读者直接看第四节（选型速查）、第七节（优缺点对照）与第八节（通用性分析）；关心「能稳定跑多大规模」直接看第九节。

**执行摘要**：多智能体框架在 2024–2025 经历「百框大战」后已进入**收敛期**。核心发现：

- **格局收敛**：两大头部确立（CrewAI 58.6k⭐、LangGraph 41.7k⭐）；AutoGen（61.0k⭐）进维护模式由微软 Agent Framework 接棒，OpenAI Swarm 归档被 Agents SDK 取代——「实验框架→生产 SDK」的换代周期完成；
- **技术重心转移**：从「多 agent 对话编排」转向「状态持久化 + 图工作流 + 跨框架互操作协议（A2A / MCP）」；
- **共识架构**：大规模集群的共识是 Anthropic 工程文章定型的 **orchestrator-worker（主控-工人）** 模式——代价是多 agent 系统 token 消耗约为普通对话 **15 倍**，token 使用量单独解释 80% 的性能方差；
- **编码 agent 是集群思想最成熟的落地**：Claude Code（145.1k⭐）与 Codex（124.3k⭐）的 subagent 机制证明 orchestrator-worker 在垂直领域已大规模可用，且已溢出到法律、金融、医疗等非编码领域；
- **集群规模上限是分层的**：Claude Code 单会话并发 subagent 默认 20（dynamic workflow 单 run 总量 1,000）、Codex 本地仅 4–6——但两家共同的真正天花板都是**用量额度**（5 小时滚动窗口 + 周额度），不是 agent 数量；
- **没有通用最优框架**：控制力 × 上手速度 × 通用性是不可能三角，通用性由协议层（A2A / MCP）承担而非单一框架。

**关键数字速览**：

| 关键数字 | 含义 |
|------|------|
| 约 15 倍 | 多 agent 系统 token 消耗相对普通对话的倍数（Anthropic 工程文章） |
| 80% | token 使用量单独解释的多 agent 系统性能方差（加工具调用数与模型选择共 95%） |
| 20 / 1,000 | Claude Code 单会话默认并发 subagent 数 / dynamic workflow 单 run 的 agent 总量上限 |
| 4–6 | Codex 本地单会话并发 subagent 线程默认值（源码常量，V2 后端实际 3 个 spawn） |
| 58.6k / 41.7k | 头部双雄 CrewAI / LangGraph 的 star 数（2026-09-15） |
| 25+ | 本报告逐仓库直查的框架与协议项目数 |

## 二、技术演进脉络：五个关键转变

### 2.1 编排范式：从对话到图

- **早期**（AutoGen / ChatDev / MetaGPT，2023–2024）：多 agent 对话 + 角色扮演，涌现行为多但难控，适合 demo 与研究。
- **现在**（LangGraph / Google ADK 2.0 / MAF / Mastra，2025–2026）：**显式图工作流**——sequential / concurrent / handoff / group collaboration 模式；支持 fan-out / fan-in、循环、重试、动态节点、human-in-the-loop、嵌套子图。LangGraph 官方定位即「低层编排框架」（low-level orchestration framework），只提供状态机原语不预设高层语义；Google ADK 2.0 的 Workflow Runtime 与 Task API 把「agent 间委派」也结构化成 API。

### 2.2 大规模集群的共识架构：orchestrator-worker

- 主 agent（Opus 级）分析任务 → 制定策略 → **并行 spawn 专业化 subagent**（Sonnet 级），各自独立上下文窗口，做「压缩式检索」后把精华回传主 agent；
- 本质：「搜索即压缩」——subagent 并行探索广阔语料，各自蒸馏出最重要 token；
- **关键数据**：多 agent 系统 token 消耗约为普通对话 **15 倍**（单 agent 约 4 倍）；token 使用量单独解释 80% 的性能方差（加上工具调用数与模型选择共 95%）。<Cite n={1} />
- 工程含义：规模化集群 = 并行烧 token 换吞吐；适用 breadth-first（多独立方向）任务，不适用 depth-first 单线深挖。

### 2.3 状态持久化成为标配

2026 年所有头部框架的共同关键词是「long-running, stateful agent」：

| 能力 | 代表 |
|------|------|
| durable execution / 断点恢复 | LangGraph（失败后从精确断点自动恢复）、MAF（checkpointing + time-travel） |
| 挂起-恢复 | Mastra（suspend → 等用户输入 → resume，可无限期暂停） |
| 短期 + 长期记忆 | LangGraph（工作记忆 + 跨会话持久记忆）、Letta（长期记忆专项） |

### 2.4 互操作协议层兴起（2025–2026 最大结构性变化）

- **MCP**（Model Context Protocol，Anthropic 发起，9.2k⭐）：agent ↔ 工具 / 数据源的标准接口，已成事实标准，各框架全部原生支持。
- **A2A**（Agent2Agent Protocol，Google 发起后捐赠 Linux 基金会，25.8k⭐）：agent ↔ agent 的发现、能力协商、长任务协作协议——**不暴露内部状态、记忆或工具**。<Cite n={4} /> AgentScope 2.0 已内置 A2AAgent 可直接对话远端 A2A agent。
- 含义：「集群」正从单框架内部编排走向**跨框架、跨组织的分布式 agent 网络**；框架竞争上移到协议层，谁的 agent 都能作为网络节点被编排。

### 2.5 框架整合与换代（淘汰已发生）

- **AutoGen**（61.0k⭐）README 挂出维护模式公告：不再有新特性，社区托管；新用户直接引导至 **Microsoft Agent Framework（MAF）**——AutoGen + Semantic Kernel 的官方合体继任者，Python / .NET / Go 三语言，主打生产就绪（稳定 API + 长期支持承诺）。<Cite n={2} />
- **OpenAI Swarm**（教育实验项目）归档，被 **OpenAI Agents SDK**（29.5k⭐，v0.22.2）取代：provider-agnostic、100+ LLM、handoffs / guardrails / sessions / tracing 全套生产件。<Cite n={3} />
- **AG2**：AutoGen 社区分叉独立演进，v1.0 转向 protocol-driven 架构（经典 ConversableAgent / GroupChat 移到独立仓库）。
- 国内格局：阿里 **AgentScope**（31.7k⭐，v2.0）、字节 **DeerFlow**（82.5k⭐，深度研究）与 CAMEL（17.7k⭐，学术）、蚂蚁 agentUniverse（2.4k⭐）多线并行。

## 三、值得注意的实现细节（一手页面核实）

- **CrewAI** 双层抽象：Crews（角色自治协作）+ Flows（事件驱动精确控制），官方称 10 万+ 开发者完成社区课程认证；商业化走 AMP 套件（托管部署 / 可观测 / 治理 / 安全），甚至为 AI 编码 agent 发布了官方 Claude Code 插件市场 skill 包。
- **LangGraph**：41.7k⭐，Klarna / Replit / Elastic 生产采用；自我定位刻意「低层」，与 LangChain 解耦可独立使用。
- **Mastra**：TS 生态事实标准（28.1k⭐），workflow 语法即代码直觉（`.then()` / `.branch()` / `.parallel()`），40+ provider 单一接口。
- **Google ADK 2.0**：Workflow Runtime（路由 / fan-out / 循环 / 重试 / 动态节点 / HITL / 嵌套）+ Task API（结构化 agent 间委派）+ 模块化多 agent 层级；⚠️ 2.0 对 agent API、事件模型、session schema 有 breaking changes。
- **MAF**：Foundry Hosted Agents（两行代码把 agent 托管到 Foundry）、OpenTelemetry 内建、YAML 声明式 agent、DevUI 调试界面。
- **smolagents**：极简主义路线，核心逻辑约 1000 行；特色 CodeAgent（agent 写代码作为动作而非被用来写代码），沙箱执行。
- **Swarms**：主打企业级预置多 agent 架构（sequential / concurrent / hierarchical……）开箱即用。

## 五、趋势判断

1. **收敛而非继续发散**：框架数量增长已停滞，star 与社区向头部（CrewAI / LangGraph）与大厂继任者（MAF / Agents SDK / ADK）集中；AutoGen→MAF、Swarm→Agents SDK 的换代标志着「实验框架→生产 SDK」周期完成。
2. **协议层成为新战场**：MCP（工具互操作）+ A2A（agent 互操作）把「集群」的定义从框架内部扩展到跨组织网络；框架价值从「编排语法」下移为「协议实现质量 + 运维能力」。
3. **规模化经济学被量化**：Anthropic 的 15× token / 80% 方差数据给行业定了调——集群编排的工程优化空间（并行度、压缩率、subagent 数量预算）成为新的研究热点。<Cite n={1} />
4. **状态与持久化是生产分水岭**：无 checkpoint / 恢复能力的框架正被挤出生产场景。
5. **编码 agent 是集群思想最成熟的落地**：Claude Code（145.1k⭐）与 Codex（124.3k⭐）的 subagent 机制证明 orchestrator-worker 在垂直领域已大规模可用。

## 六、增补：Claude Code / Codex 在 coding 之外的领域与案例

**核心发现**：两个「编码 agent」实际上已经溢出到远超 coding 的领域——法律文书、金融运营、医疗信息化、营销运营、数据处理、个人知识管理，而且 Anthropic 已经把这条路径产品化（Cowork，「Claude Code for non-coding tasks」）。它们能跨界的根本原因是：Claude Code 的本质是「**文件夹 + 终端 + 浏览器 + MCP 的通用 agent 运行时**」，代码只是它操作的一种文件类型。

### 6.2 Anthropic 官方的产品化路径：Cowork

Anthropic 已把「Claude Code 用于非编码工作」直接产品化为 **Cowork**（[claude.com/product/cowork](https://claude.com/product/cowork)）：给一个目标，Claude 跨文件与工具自主工作，用户回来验收。<Cite n={9} />官方演示场景即为**营销周报**（每周一自动从 Amplitude 拉流量 / 注册数、从 Drive 的 Channel-tracker 拉邮件 / 社交 / 网络研讨会数据、环比对比后生成 PPTX）。内置浏览器（agent 专用、与用户浏览器隔离），支持 Chrome / Edge / Firefox cookie 导入保持登录。官方文档同时明确 Claude Code 本身「works in any directory」——notes vault、文档文件夹、任何 markdown 集合都能像代码一样搜索 / 编辑 / 重组。

### 6.3 社区一手用例（r/ClaudeAI，2026 年实际运行中的工作流）<Cite n={13} />

## 八、增补：「有没有一个最优的通用框架适用于所有领域？」——没有，且短期不会有

这是本轮调研最值得正面回答的问题。**答案是明确的否定**，且有结构性的原因。

### 8.1 设计空间本身存在张力（不可能三角）

- 要**生产可控**（LangGraph 式显式图、检查点、人审）就必然牺牲「开箱即用的直觉」；
- 要**上手快**（CrewAI 角色隐喻、smolagents 极简）就必然在复杂流转上碰到抽象天花板；
- 要**通用**就要把决策留给模型，那就失去了企业要的确定性；
- 微软 MAF 试图「既要又要」（图模式 + 声明式 + 多语言），代价是概念面积大、学习成本不低——这本身就是该张力的体现。

### 8.2 任务形态差异太大，没有单一编排原语能覆盖

- 深度研究（DeerFlow）：breadth-first、并行探索、压缩回传——orchestrator-worker 最优；
- 软件工程（Claude Code / Codex）：长会话、文件系统、验证循环——单 agent + subagent 按需扇出最优；
- 客服 / 业务流（Qonto / Spellbook）：规则化、高吞吐、人工门控——显式工作流引擎最优；
- 实时语音（AgentScope RealtimeAgent）：流式、低延迟——pipeline 最优；
- Anthropic 自己都按场景拆产品（Claude Code / Cowork / Managed Agents），而非做一个「万能 agent 框架」。

### 8.3 行业正用「分层 + 协议」替代「统一框架」

2025–2026 的实际收敛方向不是「一个框架吃所有」，而是分层：

框架的价值正在从「编排语法」降为「协议实现质量 + 运维能力」——**通用性由协议层（A2A / MCP）承担，而不是由某一个框架承担**。这类似 Web 历史：没有一个「最优 Web 框架」，但 HTTP / HTML 通用。

### 8.4 选型的正确姿势：先问三个问题

1. 任务是 breadth-first 还是 depth-first？（决定 orchestrator-worker 还是长会话单 agent）
2. 交付物要确定性流程还是自主探索？（决定图引擎还是角色自治）
3. 团队技术栈与合规边界？（Python → LangGraph / CrewAI；.NET / Go → MAF；TS → Mastra；国内 → AgentScope；要跨组织互联就上 A2A + MCP）

> 一句话：**「通用性」的载体是协议（A2A / MCP）与模型能力的提升，不是某一个框架。框架选型本质是在「控制力 × 上手速度 × 生态匹配」三角里为自己的团队找位置。**

## 九、增补：Claude Code / Codex 能稳定编排的 Agent 集群规模上限（2026-09-16 调研）

**调研方式**：browser-skill 直查一手来源——Claude Code 官方文档（code.claude.com/docs 的 sub-agents / agent-teams / workflows / agent-view / agents / costs / env-vars / desktop / best-practices 九页）、Codex 官方文档（learn.chatgpt.com/docs 的 subagents / cloud / pricing / codex-sdk / git-worktrees 五页）、openai/codex 源码常量（GitHub code search 直查 `codex-rs/core/src/config/mod.rs`）、claude.com/pricing 定价页。所有数字均为当日实时核实。

**结论一句话**：两家都**不存在单一的「集群规模上限」**——真实约束是分层的：Claude Code 单会话并发 subagent 默认 **20**（可调，ultracode 豁免）、dynamic workflow 单次 run 总量 **1,000 个 agent**（并发 16）、agent teams **无硬上限**（官方建议 3–5）；Codex 本地单会话并发 subagent 默认仅 **4–6**（源码常量）；而两者共同的真正天花板是**订阅 / API 用量额度**（5 小时滚动窗口 + 周额度），不是 agent 数量——官方原文明确警告「一次大型 workflow 扇出可以在会话窗口重置前耗尽周额度」。<Cite n={10} />

### 9.1 Claude Code：分层的规模上限（逐项核实）

| 机制 | 并发上限 | 总量 / 深度上限 | 可调性 |
|------|---------|-------------|--------|
| **Subagent**（Agent 工具） | 默认 **20** 个 / 会话，到限后再 spawn 报 `Concurrent subagent limit reached` | 会话累计 spawn 数**无上限**（旧变量 `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` 默认 200，v2.1.224 已移除为 no-op） | `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 任意正整数（v2.1.217+）；**ultracode 会话完全豁免** |
| **嵌套深度** | — | 默认 **3 层**（主对话之下） | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`，设 1 关闭嵌套 |
| **工具级并行** | `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` 默认 **10**（只读工具与 subagent 的并行执行数） | — | 环境变量；官方 429 处置建议即「调低它、避免大量并行 subagent」 |
| **Dynamic workflows**（ultracode / Workflow 工具） | **16 个并发 agent**（CPU 少时自动更少，含 CPU 受限容器） | 单次 run **1,000 个 agent 总量**（防失控）；单次 `parallel()` / `pipeline()` 最多 **4,096 项** | 规模指引（advisory 非硬帽）：small 5 个以内、medium 10 个以内（Pro 计划 v2.1.271+ 默认）、large 50 个以内、unrestricted 无指引 |
| **Agent teams**（实验性，默认关闭 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`） | **无硬上限**；官方建议 **3–5** 起步（「三个专注的 teammates 常胜过五个分散的」） | 每会话仅 1 个 team；无嵌套 team；lead 固定 | — |
| **Agent view**（`claude agents`，研究预览） | 无文档化数量上限；每个后台会话是完整 Claude Code 会话 | — | 官方明示「10 个并行 ≈ 10 倍配额消耗」 |
| **/batch skill** | 一次大改动拆 **5–30** 个 worktree 隔离 subagent，各自开 PR | — | — |
| **跨会话视野** | Desktop 跨会话消息默认见**最近 20 个**活跃会话 | — | — |

**官方口径的「稳定」规模**：四个并行机制的官方定位对比表写明——subagents「每回合几个委派任务」、agent teams「一小撮长时运行的 peers」、dynamic workflows「**每 run 数十到数百个 agent**」。超过 25 个 agent 或预计 150 万 token 的 workflow 会触发 "Large workflow" 警告（advisory，不暂停）。

### 9.2 真正卡住规模的是用量额度，不是 agent 数

- **订阅（Pro / Max）**：**5 小时滚动 session 窗口 + 每周 weekly limit**，跨所有模型共享（切 `/model` 不能恢复）；Opus / Sonnet 另有家族级限额。官方原文：**「用量同时计入 session 与 weekly 两个窗口。一次重型活动爆发（如大型 workflow 扇出）可以在 session 窗口重置之前耗尽 weekly 额度」**——这是大规模集群的第一稳定性约束。
- **v2.1.199+ 的失败语义**：被 rate limit / 超载 / 服务器错误打断的 subagent 会把失败如实上报给主 agent（部分输出标记为 cut-off），而不是把错误文本伪装成调查结论——集群稳定性在「诚实失败」层面有官方保障。
- **API key 用户**：429 由 TPM / RPM 决定。官方团队部署建议：1–5 人团队每用户 200k–300k TPM / 5–7 RPM；500+ 人团队降到 10k–15k TPM / 0.25–0.35 RPM（限额按组织级共享）。企业实测均值 **$13 / 开发者 / 活跃日**，90% 用户低于 $30 / 日。
- **Claude Agent SDK**（TS v0.3.219 / Python v0.2.127+，捆绑 Claude Code v2.1.219）：默认与 CLI 相同（depth 3 / 并发 20）；spend 上限 `maxBudgetUsd` **默认无**，可设美元帽（到帽拒绝新 spawn、停后台 subagent、以 `error_max_budget_usd` 结束查询）。SDK 文档明言「一个 prompt 可以长成一棵 agent 树，每个 subagent 各自发 API 请求」。
- 降并发是官方 429 处置路径：调低 `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`、避免大量并行 subagent、或切小模型。

### 9.3 Codex：并发明显更保守

- **本地 subagents**（CLI / IDE / 桌面，`agents.enabled` 默认 true）：并发由 `agents.max_concurrent_threads_per_session` 配置（官方示例 6 与 8），**未设置时由后端选默认——源码常量**（`codex-rs/core/src/config/mod.rs`）：<Cite n={12} />
  - V1 collab 后端：`DEFAULT_AGENT_MAX_THREADS = 6` 并发线程；**V1 嵌套深度默认 1**（`DEFAULT_AGENT_MAX_DEPTH = 1`，即 subagent 不能再 spawn）；
  - V2 multi-agent-v2 后端：`DEFAULT_MULTI_AGENT_V2_MAX_CONCURRENT_THREADS_PER_SESSION = 4`（**含主线程**，即 3 个并发 spawn）。
- 内置 agent 仅三种：`default` / `worker` / `explorer`；官方建议 worker 用 `gpt-5.6-terra` / `gpt-5.6-luna` 等轻量模型。
- **Codex cloud**：可从 web / GitHub / GitLab / Linear / Slack 并行派发多个任务，**未公布硬性并行任务数上限**，受 ChatGPT 套餐额度约束（5 小时窗口消息估算：GPT-5.6 Sol 在 Plus 10–100 条 → Pro 20x 200–2,000 条；Luna Plus 250–2,000 条 → Pro 20x 5,000–40,000 条；cloud chats 用 Sol 且比本地消息更耗额度）。
- **Worktrees**：桌面端默认保留**最近 15 个** Codex-managed worktrees（并行 chats 的隔离载体，可配置）。
- **Codex SDK**（TS `@openai/codex-sdk` / Python `openai_codex`）：thread 模型（`startThread` / `thread.run`），无文档化并发上限——程序化扇出的天花板是账号级 rate limit。
- **勘误**：「Agent Network」并非 Codex 官方功能——官方文档全站索引（llms.txt）与源码中均不存在该产品（源码中 "agent network" 仅出现在网络权限管理语境）；社区 issue #35586 是关于 human-agent 网络效应的 RFC 讨论，非已发布能力。

### 9.4 对照结论

| 维度 | Claude Code | Codex |
|------|-------------|-------|
| 单会话并发 subagent 默认 | **20**（可调；ultracode 豁免） | **4–6**（源码默认，V2 实际 3 个 spawn；可调） |
| 集群总量机制 | workflow 单 run **1,000** agents / 单次扇出 4,096 项 | 未公布（云端多任务并行） |
| 官方建议的稳定区间 | teams **3–5**；workflow「**数十到数百**」；/batch **5–30** | 每会话**个位数** subagent；云端多任务 |
| 并发 agent 硬帽 | workflow **16**（受 CPU） | V2 **4** 线程 / 会话（含主线程） |
| 真实天花板 | 5h session + weekly 额度；API 则 TPM / RPM | ChatGPT 套餐 5h 窗口额度 |
| 集群无硬上限的层 | agent teams、agent view、多会话 / 多 worktree | cloud 并行任务、SDK 多 thread |

**工程含义**：若目标是「单机稳定编排几百个 agent」，Claude Code 是两者中唯一官方支持的路径——但形态是 **dynamic workflow（16 并发 × 1,000 总量，ultracode 触发）** 而非裸 subagent 堆叠；Codex 的本地多 agent 明显走保守路线（个位数并发、V1 默认禁嵌套），大规模并行要靠 Codex cloud 的多任务派发。两家的共同事实是：**集群规模的分水岭在额度经济学（第二节 Anthropic 15× token 定律），软件层的「上限」都可以调大或绕开**。规模化集群前先用官方建议的 RPM / TPM 估算扇出预算，并用 SDK 的 `maxBudgetUsd` 或 workflow 规模指引设硬帽。

## 小结

> 一句话结论：框架「百框大战」已收官，选型在「控制力 × 上手速度 × 生态匹配」三角里做减法即可；真正的集群工程问题不在「用哪个框架」，而在**额度经济学与上下文经济学**——15× token 定律决定了扇出预算，编排质量取决于压缩回传的效率。

如果只从这篇报告带走三件事，带这三条：

1. **架构选 orchestrator-worker 不会错**：它是 Anthropic 生产验证、Claude Code / Codex 内置、框架层（LangGraph / ADK / MAF）全都收敛到的同一个模式——但记住它只适用 breadth-first 任务；
2. **预算先于规模**：集群的第一约束是 5 小时窗口 + 周额度（或 API 的 TPM / RPM），「能跑多少 agent」是伪问题，「这次扇出愿意花多少 token」才是真问题——用 `maxBudgetUsd` 或 workflow 规模指引把预算显式化；
3. **通用性买不来，只能协议化**：跨框架、跨组织的集群互联走 A2A + MCP，不要赌任何一个「万能框架」。

与《[推理与任务规划调研](/frontier/model-reasoning-planning)》对照着读：那篇的结论是「模型侧把多轮能力做进权重、harness 侧堵失败模式」——本篇的 orchestrator-worker、状态持久化、验证闭环正是 harness 侧答案在「多 agent」维度的延伸。
